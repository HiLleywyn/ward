# LibreHub cracked-software loader wave

Ward recorded 40 live GitHub repositories whose pinned READMEs publish the
password `LibreHub#!` and direct users to 19 product-specific paths on
`librehub.click`. The repository-specific records are maintained in
[`malware-record-set-librehub.json`](../src/ward/advisories/malware-record-set-librehub.json).

## Confirmed artifact

Ward collected the Filmora route before the delivery service developed a TLS
protocol failure.

| Artifact | SHA-256 |
| --- | --- |
| Password-protected Filmora ZIP | `b4b59ebd4c1fd958ad0b91f400221a9191c00fe409a3ba533b1656cd0654df24` |
| `Installer.exe` | `400b6b3003a85813cf6553c51ae0e24f7652c49d84131a895cb27e9c30bd2cc0` |
| Reconstructed runtime stream | `da36fdaa79a3b919d506fba9a09906c8e4df2e626769743e8ac3d1dfd440ac15` |

The archive was extracted and the PE was inspected only inside
`ward-remnux:0.8.0` with networking disabled and read-only sample mounts. No
archive member or recovered byte stream was executed.

## Static mechanism

The loader stores its runtime in section `.fba6a2`. It retains the first eight
bytes of every 32-byte block, concatenates those bytes, and XORs the result with
an embedded 16-byte key. The recovered code decrypts these values:

- `Elevation:Administrator!new:{3E5FC7F9-9A51-4367-9063-A120244FBEC7}`
- ICMLuaUtil IID `{6EDD6D74-C007-4E75-B76A-E5740995E24C}`
- `C:\Windows\explorer.exe`
- relaunch marker `RQFTIRXS`

The decompiled call path initializes COM, calls `CoGetObject` for the
auto-elevated ICMLuaUtil object, and invokes its `ShellExec` method on the
current process image with `SW_SHOW=5`. Before relaunch, a separate routine
rewrites the PEB process parameters and the current module's loader-list name
fields to present the executable as `C:\Windows\explorer.exe`.

The combination is a deliberate auto-elevation and process-masquerading loader,
not expected cracked-installer behavior.

## Reproducible extraction

Ward includes [`extract_pe_stride_xor.py`](../tools/extract_pe_stride_xor.py), a
bounded static extractor for this packing pattern and similar variants:

```powershell
python tools/extract_pe_stride_xor.py Installer.exe `
  --section .fba6a2 --block-size 32 --retain 8 `
  --key-rva 0xf3180 --key-length 16 `
  --output carrier-runtime.bin
```

The tool validates PE and section bounds, reports repeated filler structure,
and writes bytes only when requested. It never loads or executes the input or
output.

## Evidence boundary

The 40 pinned READMEs prove participation in the same LibreHub delivery service
and preserve each repository separately in Ward. The collected Filmora route
proves the loader behavior above. Later checks reached Cloudflare over HTTP but
failed during HTTPS negotiation in curl and a real browser, so the other 18
route IDs could not be re-collected. Ward does not claim those archives were
byte-identical, identify the GitHub account operators, or assign a final payload
family beyond the confirmed loader behavior.
